**Minutes** by Tim Davis

We decided to propose to ditch the "vanilla" idea in LAGraph, and assert the
use of SuiteSparse:GraphBLAS.  It's too hard to support.  Reasons:

    (1) keeping the "vanilla" becomes harder as SuiteSparse:GraphBLAS improves.
    (2) there is no other usable high-performance GraphBLAS library.
    (3) there is no active GraphBLAS C API committee, so new features like
        GxB_IndexBinaryOp will remain GxB for a very long time.
    (4) CUDA development will add another revision to LAGraph_Malloc and
        LAGraph_Free; those methods will need to add parameter to give the
        memory arena (0: default malloc/free, others for each GPU, etc)
    (5) too many experimental algorithms use GxB features; many can be revised
        to do GrB-work instead, but the developers of those algorithms are not
        interested in doing that.  It's too much extra work.  Worse, some
        algorithms are completely different (see the BFS in the src folder).
        This takes more development work, which is hard to justify to support
        the use of a non-existent vanilla GraphBLAS library.

Do we use `GrB_Scalars` where possible, for all input/output scalars?  Or just
in some methods?  In our last meeting, we decided to use GrB scalars only
where the result would depend on the graph matrix data type.  MaxFlow is
the only case, where it returns the total flow as a sum of edge weights.
