## Agenda and Minutes

**Agenda** by Tim Davis

To discuss:  replacing C pointers to array with `GrB_Vectors`, and replacing C
input/output scalars with `GrB_Scalars`.  This will cause additional breaking
changes in the src/ methods, if we make this change.  For example,
`LAGr_Betweenness` takes as input `uint64_t *sources` and `int32_t ns`.  This
could be replaced by a single `GrB_Vector sources`, as is already done in
`LAGr_EdgeBetweennessCentrality`.  (So should `LAGr_Betweenness` be renamed to
`LAGr_VertexBetweennessCentrality`?)

Adding this `GrB_Vector` would also require a descriptor or flag to state which
list of indices should be used for a vector v:  the indices I or values X from
an implicit `GrB_extracTuples (I, X, v)` on the vector.

**Minutes** by Tim Davis

We discussed the LAGraph API, using this spreadsheet:
https://docs.google.com/spreadsheets/d/1-WnAsmrHRYh5KQeJZzMtZYZKiKblGKYOOIkw0MdokuU/edit?usp=sharing

We determined that several LAGr experimental algorithms and one LAGr
src algorithm (connected components) modifies its input graph.  This
needs to be revised to ensure the LAGr expert methods do not change
any input graph.

We discussed the input GrB-Vectors for passing in lists of source nodes and
whether or not we needed a descriptor to specify "by value" or "by index".
No decision was made, except to note that only a few LAGraph methods require
this.  We could instead add helper utilities to extract out the pattern of
a vector into another GrB-Vector, and have all LAGraph methods use
"by value".  GraphBLAS itself has this descriptor option, for the
vector-input-variants of `GrB_assign`, `GxB_subassign`, `GrB_extract`, etc.

Adding a descriptor to all LAGraph methods would be difficult since we
have many algorithms with many different needs.

We also discussed using an LAGraph descriptor to pass in details of which
hardware to use.  However, this could be handled with the GraphBLAS
`GxB_Context` object.
